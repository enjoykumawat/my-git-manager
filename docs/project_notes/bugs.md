### 2026-08-17 - `update_article`/`create_article`'s optional parameters were bare non-Optional annotations with `None` defaults — FastMCP's generated schema advertised `null` as the default while rejecting it as a value

- **Issue**: `update_article(article_id, title: str = None, body_markdown: str = None, published: bool = None, confirm: bool = False, expected_fingerprint: str = None)` and `create_article(..., tags: list[str] = None, ...)` both rely on `None` meaning "leave this field unchanged" — `if title is not None: article["title"] = title`, repeated per field. FastMCP builds each tool's pydantic validation model from the *annotation*, not the default, so `title: str = None` schema'd as a required `"type": "string"` field whose `"default"` was `null` — a self-contradictory schema that told callers `null` was valid while the validator rejected it outright. Verified live through a real, installed `mcp` package (not a stub): `await mcp.call_tool("update_article", {"article_id": 42, "title": None})` raised `Input should be a valid string [type=string_type, input_value=None, input_type=NoneType]` before `update_article`'s own body — and its confirm gate, staleness check, and "no fields to update" guard — ever ran. Omitting the key entirely was the only working way to mean "don't change this"; the same five previously-optional params (`title`, `body_markdown`, `published`, `expected_fingerprint` on `update_article`; `tags` on `create_article`) all reproduced it identically.
- **Root Cause**: Five separate prior hardening passes on `update_article` (the confirm gate, the fingerprint staleness check, the duplicate-title guard, the empty-payload guard, the fetch-before-write diff/log) all called the function directly as plain Python in `--selftest` — bypassing FastMCP's pydantic layer entirely. A bare `str` annotation with a `None` default reads as optional to any human skimming the signature, and behaves as optional when called directly in Python (the default just applies) — but pydantic takes the annotation at face value, independent of the default, and none of those five passes ever drove a call through the actual `mcp.call_tool()` path a real MCP client uses.
- **Solution**: Changed the five affected parameters to `str | None` / `bool | None` / `list[str] | None`. The regenerated schema now correctly emits `"anyOf": [{"type": "string"}, {"type": "null"}]`, and the identical `title: None` call now reaches `update_article`'s own `"no fields to update"` `ValueError` — the same outcome as omitting the key. Added a new `--selftest` block that drives the real `mcp.call_tool()` async path via `asyncio.run()` against the real installed `mcp` package, specifically because a stub built to make `--selftest` importable without the dependency wouldn't reproduce pydantic's validation behavior at all. `server.py --selftest` and all other selftest-bearing scripts in the repo pass.
- **Prevention**: A parameter meant to accept `None` as a real, callable value — not just a default that silently applies when the key is omitted — needs an actual `Optional`/`| None` annotation, not just a `None` default on a bare type; the two look interchangeable to a human and to a direct Python call, but a framework that derives its wire schema from annotations (FastMCP via pydantic) treats them as completely different contracts. Testing a tool by calling its Python function directly, however many cases accumulate, never exercises the schema-validation layer a real MCP client actually goes through — that requires calling through the real `mcp.call_tool()` path at least once.

### 2026-08-17 - `reply_comments.py`'s `audit()` matched drafted replies against thread-root id_codes only, missing the nested/branching id_codes `pending()` has drafted against for weeks

- **Issue**: `audit()`'s outer loop iterated straight over `api(f"/comments?a_id=...")`'s return value — the THREAD ROOTS only, one entry per top-level comment — and checked `c["id_code"] not in drafted_codes` against just that level. That was complete back when `pending()` only ever drafted a reply keyed on a thread's root comment. It stopped being complete the moment `pending()` itself was fixed to draft against non-root id_codes: the 2026-08-02 fix (a follow-up nested under my own reply becomes its own pending entry, keyed on THAT comment's id_code) and the 2026-08-12 `_pending_leaves()` fix (a branching thread drafts against each unanswered LEAF's id_code, at whatever depth it sits) both moved `drafted_codes`' normal contents to include non-root codes as the ordinary case, not the exception — and nothing in `audit()` moved with them. Verified live end-to-end through the real `audit()` (not a stubbed helper): a root comment "aaa" with my reply "myreply1" nested under it, and a fresh follow-up "bbb" nested under my reply, drafted in `comment_replies.md` as `## bbb` but never actually pasted on-site. `audit()`'s outer loop checked `"aaa" not in drafted_codes` (true — "aaa" was never drafted), skipped the whole thread, and never looked at "bbb" at all. Real result: `{"drafted": 1, "never_posted": []}` — a drafted-but-unposted reply reported as fully handled.
- **Root Cause**: The 2026-08-01 fix to this same function (`replied_anywhere_in_subtree()`, this file, above) fixed the *inner* question — "given a comment, did I ever reply anywhere below it" — by making that check recursive. It never touched the *outer* question — "which comments are even candidates to check in the first place" — which stayed a flat, root-only iteration. Two later, unrelated fixes to `pending()` (2026-08-02, 2026-08-12) changed what `drafted_codes` actually contains in production without anyone re-checking whether `audit()`'s own traversal still covered it; the two functions are meant to be a matched pair (one drafts against an id_code, the other checks whether that same id_code got a live reply) and quietly drifted out of sync.
- **Solution**: Added `_walk_comments()` — yields a comment and every comment in its subtree, at any depth, same recursive shape as `_pending_leaves()`. `audit()` now checks `c["id_code"] in drafted_codes` for every node `_walk_comments()` yields per thread root, not just the root itself. Added a selftest case reproducing the exact scenario above through the real `audit()` (stubbed `api()`/`DRAFTS`, not the standalone helpers): before the fix, `never_posted` was empty; after, it correctly reports `bbb`. `reply_comments.py --selftest` passes; `server.py`, `publish_devto.py`, `git_commit.py`, `scripts/check_key_facts.py`, `scripts/list_all_published_titles.py`, and `scripts/score_published.py` selftests all still pass, unaffected but rerun to rule out sideways breakage.
- **Prevention**: When two functions are a matched pair over the same data shape — one produces a set of keys, the other consumes that same set — a fix to what the producer emits needs to be checked against every consumer's assumptions about that shape, not just re-verified against the producer's own tests. `pending()` picked up two fixes that changed the depth of id_codes it drafts against; `audit()`, the only other place those exact id_codes get looked up, was never part of either fix's blast-radius check.

### 2026-08-15 - `update_article`'s confirm gate checked that the caller meant to write. It never checked that the article was still what the caller reviewed

- **Issue**: The confirm gate shipped earlier the same day (this file, below) stops an *unconfirmed* write to a published article, but does nothing about a *stale confirmed* one. `before` is re-fetched fresh on every call, including the confirmed one, so the function has the evidence a live edit landed in between the preview and the approval — it just never compared against it. Surfaced by a real reader comment on the article about the confirm gate itself (`mads_hansen_27b33ebfee4c9`, comment `3d3hj`, same day): a preview computed from version A, someone else edits the article to B, the caller's already-approved `confirm=True` call still fires and silently overwrites B with whatever was approved against A. Verified live with a stubbed `_dev()`: preview → simulated out-of-band edit → the confirmed call proceeded and clobbered the intervening change, with no warning it had happened.
- **Root Cause**: The confirm gate was built and tested against "did the caller mean to write" — a question about caller intent — and never separately asked "does the write still describe the current article," a question about the target's state. Both questions happen to be answered by the same `before` fetch, which made it easy to assume checking one covered the other.
- **Solution**: Added `_article_fingerprint(before)` (sha256 of `title`+`body_markdown`, truncated) returned in the preview response. A caller passes it back as an optional `expected_fingerprint` param on the confirmed call; a mismatch against the freshly-fetched article's current fingerprint refuses the write as stale (`applied: False`, fresh diff+fingerprint returned) regardless of `confirm`. Deliberately opt-in: omitting `expected_fingerprint` preserves the exact behavior shipped earlier today, since a caller that never previewed and is knowingly forcing a specific title/body is a legitimate, different case this shouldn't block. 4 new selftest cases (stale-confirm blocked with zero PUTs, fresh-fingerprint confirm applies, backward-compat no-fingerprint still applies unchanged). `server.py --selftest` passes; all other selftest-bearing scripts unaffected and rerun to confirm.
- **Prevention**: A confirmation step proves the caller's intent at the time they gave it; it says nothing about whether the target still matches what that intent was formed against. When a write is gated because it's irreversible, the gate needs to check the target's current state against what was actually reviewed, not just that some earlier review happened at all — especially when the two steps (preview, approve) can be separated by an arbitrary amount of real time.

### 2026-08-15 - `create_article`'s duplicate-published-title guard only runs on its own codepath — `update_article` can reach the identical live outcome two other ways it never covered

- **Issue**: `create_article`'s duplicate check (issues.md 2026-08-03) only fires for a POST made with `published=True`, and is skipped entirely for drafts by design (two drafts sharing a title costs nothing). `update_article` can put an article into the same live state — this account showing two published articles with an identical title — through two paths that guard has never touched: publishing a draft via `update_article(id, published=True)` whose title happens to collide with a different already-published article, or renaming an already-published article onto another live article's exact title via `update_article(id, title=...)`. Verified live with a stubbed `_dev()`: a draft whose title matched a different, already-published article's title was published via `update_article(id, published=True)` — call trace was one GET, one PUT, zero lookups against `/articles/me/published`, i.e. no duplicate-title check anywhere on this path at all.
- **Root Cause**: The 2026-08-03 guard was written and verified against the one call path that was actually breaking at the time (a POST retried after an ambiguous timeout). Nobody separately asked whether a *different* function could reach the same live state the guard exists to prevent — `update_article` computes "will this article end up published under this title" completely independently of `create_article`, so a check scoped to the POST path structurally can't see a write that goes through PUT instead.
- **Solution**: Added `_duplicate_published_title(article_id, final_title, final_published)`, which computes the title/published state a given `update_article` call would actually leave behind (merging the call's fields with the article's current ones) rather than branching on what kind of call it is, and checks it against every other currently-published title (excluding the article's own id, so editing an article under its own existing title is never flagged as a duplicate of itself). Wired in unconditionally, before the confirm/staleness gates, with no override — unlike an intentional overwrite of your own article, there's no legitimate reason to want two of your own articles live under the same title. 3 new selftest cases (draft-publish onto a duplicate refused with zero PUTs, rename onto a duplicate refused, self-id match correctly not flagged); one pre-existing stub needed a small patch to answer the new lookup it now triggers. All 7 selftest-bearing scripts in the repo still pass.
- **Prevention**: A guard's real scope is every codepath that can produce the state it's meant to prevent, not the one codepath that was actually failing when the guard was written. When two different functions can independently reach the same live outcome (here: an article ending up published under some title), a check added to only one of them protects a state, not a state-producing mechanism — the second function needs its own instance of the same check, computed from what *it* would leave behind, not copy-pasted logic from the first.

### 2026-08-15 - `update_article`'s fetch-before-write diff and audit log record that a live article changed after the PUT that changed it already landed — nothing before the PUT ever asked whether it should happen

- **Issue**: The 2026-07-27 fix (fetch-before-write diff) and the later audit-log fix both make a bad write to a *published* DEV.to article visible after the fact. Neither stops it. `_gh()`, this same file's GitHub API helper, has an unconditional hard block against any non-GET call, specifically because `GITHUB_TOKEN` is scoped `repo, user` (full write) while every GitHub tool here only ever needs to read (`bugs.md` 2026-08-11). `_dev()` has no equivalent, because `create_article`/`update_article` legitimately need to write sometimes — but "sometimes legitimately writes" had been silently treated as "writes unconditionally whenever called," which isn't the same claim. DEV.to has no version history for an article; overwriting a live, already-read `title`/`body_markdown` is not recoverable by any means this account has access to, unlike a draft (nothing lost, just re-PUT) or a bare `published` toggle (reversible by toggling back).
- **Root Cause**: Both prior fixes to this tool treated "leaves no trace" as the failure mode to close, and closed it correctly for that framing — but neither ever asked the different question of whether the write itself should be gated, since gating wasn't what either bug was about at the time it was found.
- **Solution**: Added `confirm: bool = False` to `update_article`. Computed `live_content_write = before.get("published") and ("title" in article or "body_markdown" in article)` from the same `before` fetch the diff already uses; when true and `confirm` is not set, returns the proposed diff with `"applied": False` and never calls the PUT. Confirmed calls proceed exactly as before, now also carrying `"applied": True`. Drafts and `published`-only toggles never hit the gate, since neither loses anything irrecoverable. Added 3 selftest cases against a stubbed `_dev()`: unconfirmed write to a published article blocks and reaches zero PUT calls; the same call with `confirm=True` applies and reaches exactly one; a draft applies with no confirm required at all. `server.py --selftest` passes in full (verified via the documented FastMCP-stub-on-PYTHONPATH technique, no `mcp` package in this sandbox).
- **Prevention**: A diff/log fix that makes a bad write visible answers "what happened," not "should this happen" — when a write is genuinely irreversible (no version history, no undo), a trace after the fact is a strictly weaker guarantee than a check before it, and the two aren't substitutes for each other even though a diff can look, superficially, like it's already doing the safety work.

### 2026-08-14 - `publish_devto.py`'s idempotency guard has an unfixable-from-here race window between the duplicate check and the POST

- **Issue**: `already_published()`'s two prior fixes (2026-08-07 pagination, 2026-08-08 fail-open-on-`URLError`) both closed gaps in what a *single* call to the guard could see. Neither, nor anything else in `main()`, addresses what happens when *two* invocations of the whole check-then-POST flow run at the same time: there is no lock, reservation, or atomic check-and-set between the GET that confirms a title isn't published yet and the POST that publishes it. Verified live with two real threads racing against a shared fake dev.to (a `threading.Barrier` forcing both past the "not published" check before either was allowed to post, removing luck from whether the window gets hit): both threads' `already_published()` call correctly reported "not published," both proceeded, and two live duplicate articles with the identical title resulted. This repo's own scheduled publishing task runs as a fresh container per session with no state shared between runs (`bugs.md` 2026-07-18) and is designed around sequential, non-overlapping firings — but this repo also has a documented history of runs stretching long (`claude -p` timeouts fixed 2026-08-06/2026-08-11, network stalls, an unbounded-diff `OSError`), any of which could push one run's wall-clock past the next scheduled firing.
- **Root Cause**: `already_published()` + POST is a classic time-of-check-to-time-of-use (TOCTOU) shape — correctness of the check is a claim about one execution, and every previous fix to this function was verified with a single-threaded stubbed repro, which structurally cannot surface a bug that only exists across two concurrent executions.
- **Solution**: Not fixed. The obvious patch — a local lock file (`fcntl.flock`) around the check-and-post block — was written, then deliberately not shipped: this pipeline's own architecture (fresh container per session, nothing persisted between runs except what's already pushed to git) means two overlapping runs are, by construction, two different containers with two different filesystems. A lock file in one container is invisible to the other; it would pass every local test and do nothing against the actual failure mode this repo can produce. A real fix requires either the external scheduler guaranteeing non-overlapping firings, or DEV.to's `POST /api/articles` accepting an idempotency key so two POSTs with the same key collapse into one article server-side — neither exists today, and neither is something this script can add on its own. Flagged, not fixed, same restraint as the 2026-07-19 stop-hook entry.
- **Prevention**: A check-then-act guard's tests should force the interleaving that actually breaks it (a barrier, an explicit two-thread race) rather than rely on a single-threaded stubbed repro, which can only ever prove the guard is correct for one execution at a time — a claim that says nothing about what happens across two.

### 2026-08-14 - `_claude()`'s `--safe-mode` flag isolates config discovery, not the ambient environment — `GITHUB_TOKEN`/`DEV_TO_API` were handed to the `claude -p` child anyway

- **Issue**: Both `server.py`'s `_claude()` and `git_commit.py`'s inline `claude -p` call (`bugs.md` 2026-08-10's `--safe-mode` fix) invoke `subprocess.check_output` with no `env=` kwarg. Python's documented default for that case is to copy the *entire* parent environment into the child — which, by the time either call runs, includes `GITHUB_TOKEN` (scoped `repo, user`, full write, per `key_facts.md`) and `DEV_TO_API`, both loaded into `os.environ` at import via `load_env()`. Neither call has ever needed either credential; its only job is turning a diff string into a commit-message string. `--safe-mode` drops CLAUDE.md/skills/plugins/hooks/MCP-server auto-discovery — a completely separate isolation axis from ambient environment variables, which it says nothing about. Verified live with a stub `claude` binary invoked with the exact real call shape (no `env=`): it read both credentials straight out of its own `os.environ`.
- **Root Cause**: The 2026-08-10 `--safe-mode` fix closed the specific gap it was written for (CLAUDE.md/MCP-server auto-discovery) and was verified against exactly that — nobody separately audited what `subprocess.check_output`'s own default `env=None` behavior does, since that's an orthogonal property of the `subprocess` call itself, not of anything `claude -p`'s own flags control.
- **Solution**: Added `_CLAUDE_SUBPROCESS_ENV_EXCLUDE = ("GITHUB_TOKEN", "DEV_TO_API")` and `_claude_subprocess_env()` (builds `os.environ` minus those two keys) in both files; wired `env=_claude_subprocess_env()` into both `subprocess.check_output` calls. Chose subtraction over reconstructing a minimal environment from scratch, since the real `claude` binary's own requirements (PATH, HOME, OAuth session lookup) aren't fully known from inside this sandbox. Reran the identical repro against the fixed code: `SAW_CREDENTIALS:none`, with `PATH` confirmed still present in the child's environment. Added a regression case to both files' `--selftest` blocks (sets both credentials, asserts both absent from `_claude_subprocess_env()`'s output while `PATH` survives). `git_commit.py --selftest` passes; `server.py --selftest` verified via the documented `FastMCP`-stub-on-`PYTHONPATH` technique (no `mcp` package in this sandbox).
- **Prevention**: A subprocess isolation flag's name and documentation describe what *that flag* controls — they're not evidence the subprocess call as a whole is isolated. `subprocess.check_output`/`subprocess.run` inherit the full parent environment by default regardless of any CLI flags passed to the child program; if secrets are loaded into `os.environ` anywhere upstream of a new subprocess call, that call gets them for free unless `env=` says otherwise, independent of how hardened the child command's own flags look.

- **Prevention**: An allowlist added to excuse one specific, already-vetted occurrence of a string is a different thing from an allowlist that excuses the string everywhere — the former needs the exemption scoped to *where* the vetting actually happened, not just *what* string it was about, or a fix built to stop a doc from asserting a phantom file as real can end up quietly protecting a second, unrelated instance of the exact same false claim from ever being caught. When a correction/exemption note explains why some past text was wrong, check whether the same wrong claim survives anywhere else in the document before trusting the correction to be complete.

### 2026-08-12 - `reply_comments.py`'s `pending()` only ever surfaced one leaf per top-level thread — a thread that branches into two commenters silently lost one of them, permanently

- **Issue**: `needs_reply()`/`latest_message()` recurse a comment's whole subtree and return the single message with the latest `created_at` anywhere in it; `_pending_entry()` (the 2026-08-02 fix for the "dedup keyed on the root, not the actual pending message" bug) built directly on top of that, returning at most one entry per top-level comment. That's correct for a thread that only ever grows one message at a time — root, my reply, their follow-up, my reply, and so on — which is the only shape every existing selftest case and the 2026-08-02 writeup ever modeled. It's wrong the moment a thread *branches*: two different commenters both replying to the same parent comment (my reply, say) as siblings, not to each other, which dev.to's actual comment-tree shape allows and nothing in this pipeline's design ever assumed away. - **Root Cause**: `latest_message()`'s recursive walk was written to answer "who spoke most recently in this subtree," a well-defined single-winner question — but `_pending_entry()` then used that single winner as a proxy for "is there anything pending in this thread," a question a branching tree doesn't reduce to one answer. The 2026-08-02 fix (this same file) correctly diagnosed and fixed the *previous* bug in this area — a dedup key stuck on the wrong node — but every case it tested, and the two prior fixes to `needs_reply()`/`audit()` before it, all used strictly linear parent-child chains; nothing in this file's test history ever modeled two siblings replying to the same comment, so the single-latest-leaf assumption baked into `latest_message()` was never checked against a shape it doesn't handle.
- **Solution**: Added `_pending_leaves(comment)`, a generator that walks the full subtree and yields *every* leaf (childless comment) not authored by `ME` — not just the one with the latest timestamp. Added `_pending_entries(comment, drafted_codes)`, which turns each undrafted leaf into an entry dict (same shape `_pending_entry()` used to return one of). `pending()` now iterates `_pending_entries()` per top-level comment instead of taking one optional entry. `needs_reply()`/`latest_message()` are left in place unchanged — still correct for what they specifically answer, just no longer the sole mechanism `pending()` relies on. Verified live: the userB/userC repro above now returns both `sibB` and `sibC` as separate entries; re-running with `sibC` already in `drafted_codes` still correctly surfaces `sibB` alone. Reran every existing selftest scenario (single comment, answered, followed-up, nested-reply, round-1/round-2 dedup) against `_pending_entries()` in place of `_pending_entry()` — all produce the same results as before, since a strictly linear thread only ever has one leaf. - **Prevention**: A recursive tree-walk that's designed to return a single "winner" (latest, deepest, whatever) is a red flag for any caller that actually needs "all the open items," not just one representative one — check whether the tree shape the function was tested against (a chain) is the only shape the real data can take (here: dev.to comment trees can branch) before treating a single-winner helper as sufficient for a "what's pending" query.

### 2026-07-01 - pnpm-workspace pre-commit hook broken on Windows (misleading `ENOENT: git`)
- **Issue**: While committing a fix in `vercel/eve` (a pnpm/Turborepo workspace), `git commit` failed every time with `Error: spawnSync git ENOENT`, seemingly unable to find `git` even though it was on PATH (verified from both git-bash and PowerShell).
