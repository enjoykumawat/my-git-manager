### 2026-08-07 - `reply_comments.py` fetched "my articles" with no `page` param — the API silently omitted the 2 newest ones
- **Issue**: `pending()` and `audit()` both fetched the account's own articles via `api(f"/articles?username={ME}&per_page=100")`, with no `page` parameter. Verified live against the real API: that exact call consistently returns 98 of this account's 100 published articles, missing precisely the 2 most recently published ones (both published earlier today) — while the identical call with `&page=1` added returns all 100, in the same newest-first order, the 2 missing ones right at the front. Comments on an article this pipeline can't even see don't exist as far as `pending()`/`audit()` are concerned: a real, currently-live pending comment on one of today's two new articles was silently invisible to `pending()` before this fix, confirmed by rerunning it against both the unfixed and fixed code.
- **Root Cause**: Unconfirmed on Forem's side (no server-side visibility from this repo), but the behavior is reproducible and consistent: omitting `page` does not behave like `page=1` on `GET /articles?username=...` — it returns a shorter, seemingly cached/stale result missing the newest items, while every other call site in this repo that hits a paginated dev.to endpoint (`scripts/list_all_published_titles.py`, `publish_devto.py`'s `already_published()`) already passes `page` explicitly. This one code path never did.
- **Solution**: Added `my_articles()`, which walks `page=1, 2, 3, ...` until an empty page comes back, mirroring the pattern `scripts/list_all_published_titles.py` already established for a different endpoint. `pending()`/`audit()` now call `my_articles()` instead of the single unpaginated request. Verified live: the old single-call code returns 98 articles and is missing today's two newest; the paginated walk returns all 100, including both. `reply_comments.py --selftest` now covers the pagination-walk contract (2 full pages + 1 empty, stops only on the empty page) with a stubbed `api()`.
- **Prevention**: An unpaginated call to a paginated endpoint isn't safe just because the response fits under `per_page`'s cap — some Forem endpoints return a different (and in this case shorter) result when `page` is omitted vs. explicitly `1`. Don't assume "no `page` param" defaults to "page 1"; test it against the live endpoint before trusting a single `per_page=N` call to mean "everything."

### 2026-08-07 - `list_repos`'s `limit` parameter was never validated — a negative value used Python's own negative-index slicing instead of returning nothing
- **Issue**: `list_repos`'s docstring claims `limit: 1-100`, but nothing checked the value against that range before using it in `repos[:limit]` (or, for `sort=stars`/`sort=forks`, `sorted(repos, ...)[:limit]`). Python slicing treats a negative index as "count from the end," not "invalid" — `limit=-1` silently returned every fetched repo except the last one, `limit=-3` returned all but the last three, instead of an error or an empty list. Verified live with a stubbed `_gh` returning 5 fake repos: `list_repos(limit=-1)` returned 4 of them; `list_repos(limit=-1, sort="stars")` did the same after ranking.
- **Root Cause**: `min(limit, 100)` (added for the `sort=stars`/`forks` fix, 2026-08-06) only ever clamped the upper bound; the lower bound was never checked, so any negative value passed straight through to a Python slice operation that has well-defined but non-obvious behavior for negative indices.
- **Solution**: `limit` is now clamped with `max(0, min(limit, 100))` before it's used anywhere. Reran the identical repro against the fixed code: `limit=-1`, `limit=-3`, and `limit=-1, sort=stars` all now correctly return `[]`; `limit=999` still clamps to 100 (or fewer, if fewer repos exist) as before. Added a `list_repos` case to `server.py --selftest` (verified against a stubbed `_gh` — `mcp` isn't installed in this sandbox, so also verified with a minimal `FastMCP`-stub module on `PYTHONPATH` that the full `--selftest` run passes end-to-end, not just the extracted function).
- **Prevention**: Clamping only the upper bound of a numeric parameter isn't the same as validating it — check both directions, and remember that Python's slice/index semantics quietly accept negative numbers with a real (if surprising) meaning, rather than raising on them the way a naive reader might expect.

### 2026-08-07 - `list_articles` called the wrong DEV.to endpoint — drafts, not just published articles, could crowd out the real list
- **Issue**: `server.py`'s `list_articles` docstring promises "List your published DEV.to articles," but the tool called `GET /articles/me` — Forem's API returns *every* article on that endpoint, unpublished drafts sorted first (creation order), published articles after (publication order). With `per_page` truncating the response, any account holding at least `per_page` drafts gets back an all-draft page and zero real published articles, no error, no signal anything was wrong. `list_articles` had never been individually audited before — every prior pass through `server.py` grouped it in with `create_article`/`update_article`/`get_article_stats` for the shared `_gh`/`_dev` exception-handling fix, never checked its own endpoint choice against its docstring.
- **Root Cause**: Forem exposes four near-identical endpoints for a user's own articles — `/articles/me`, `/articles/me/published`, `/articles/me/unpublished`, `/articles/me/all` — and the code called the bare, unsuffixed one instead of the `/published` one the tool's docstring and purpose actually describe.
- **Solution**: Verified live with a stubbed `urlopen` returning 12 unpublished drafts followed by 5 real published articles (matching Forem's documented sort order): unfixed `list_articles()` at its default `per_page=10` returned exactly the 12... well, the first 10 of them — all drafts, `published: False` on every row, no real article present. - **Prevention**: When an API offers several similarly-named endpoints for different subsets of the same resource, don't assume the shortest/first one found is the right one — check it against the exact subset the caller's docstring promises, the same way a parameter's accepted values need checking against the real API contract.

### 2026-08-06 - `publish_devto.py`'s `parse()` crashed with a bare `ValueError` on unclosed frontmatter
- **Issue**: `parse()`'s `_, fm, body = text.lstrip().split("---", 2)` assumes a `---`-opened frontmatter block always has a matching closing `---`. A draft with the fence opened but never closed (truncated generation, a hand-edited draft missing the closing line) makes `split` return 2 parts instead of 3, and the 3-way unpack raises `ValueError: not enough values to unpack (expected 3, got 2)`, uncaught — the only failure path in this script that didn't exit through its own `ERROR:` convention.
- **Root Cause**: Every prior audit of this file grepped for `urlopen(`/`subprocess.check_output(`-shaped bugs (missing timeouts, missing except blocks, retry safety). `parse()` touches neither — it's pure string parsing over locally-read file content — so it was never in scope for any of those passes.
- **Solution**: `parse()` now checks `len(parts) < 3` and raises a descriptive `ValueError` instead of letting the unpack fail bare; `main()` wraps the `parse()` call in `try/except ValueError` and exits through the same `ERROR: {e}` convention every other failure path already uses. Verified live: malformed-frontmatter repro before the fix produced a raw traceback; after the fix, `ERROR: frontmatter opened with '---' but never closed with a second '---' delimiter`, exit 1.
- **Prevention**: A file's error-handling convention isn't verified by checking the paths that already follow it — check the one code path that runs *before* any of those checks (here: parsing the input itself) for the same rigor.

### 2026-08-06 - `git_commit.py`'s 2026-07-23 timeout fix only covered one of the two subprocess calls it claimed to cover
- **Issue**: The 2026-07-23 fix's own writeup states "neither `subprocess.check_output` call in `git_commit.py` ... had a `timeout` ... Fixed both." The actual commit (`2f9d850`) only added `timeout=20` to the `claude -p` call; `subprocess.check_output(["git", "diff", "--staged"], text=True)` was never touched and remained untimed for 14 days.
- **Root Cause**: The writeup's "fixed both" claim was never re-checked against the shipped diff. Reran with `timeout 25` (slack above the internal bound): script now exits cleanly at ~20s with its own message and exit code 1.
- **Prevention**: "Fixed both" in a bug writeup is a claim, not a guarantee — a fix described as covering N call sites isn't verified until you've reread the actual diff and counted N, not just reread the prose that describes it.

### 2026-08-04 - `scripts/sync-main.sh` only handled a detached HEAD *ahead* of `main`, not *behind* it
- **Issue**: The ancestor check only tried `git merge-base --is-ancestor main "$head_sha"` (is `main` an ancestor of the detached commit — i.e. detached HEAD is ahead). If that's false, the script fell straight to "needs manual review" and exit 1, even when `head_sha` was actually *behind* `main` — a case that's trivially safe (every commit at `head_sha` already exists on `main`; checking out `main` loses nothing).
- **Root Cause**: The script's own comment already documents the mechanism that can produce this: sessions are provisioned by checking out a pinned commit SHA rather than the `main` ref, so a fresh/resumed container can land on a SHA older than `main` if the pin lags a push from a previous session — not just newer, which is the only direction the 2026-07-18 fix and its two follow-ups (2026-07-22 origin-fetch staleness, 2026-07-27 hook-install side effect) ever tested against.
- **Solution**: Reproduced live in a scratch repo — commit A, then commit B on `main`, HEAD detached back at A (simulating a stale pinned checkout). Confirmed `git merge-base --is-ancestor main "$head_sha"` is false (main is ahead, not an ancestor) while `git merge-base --is-ancestor "$head_sha" main` is true (head_sha is fully contained in main), and the unfixed script hit the "needs manual review" exit 1 for this fully-recoverable case. Added an `elif` branch: when `head_sha` is an ancestor of `main`, `git checkout main` directly (no merge needed, nothing to fast-forward).
- **Prevention**: A "detect divergence" branch condition that only tests one direction of a two-directional relationship (ahead/behind, newer/older) isn't complete until you've reproduced the other direction too — especially when the script's own comments already describe a root cause that can produce either one.

### 2026-08-04 - `hooks/prepare-commit-msg`'s "fixed" path resolution only works for one of the two install methods `README.md` documents
- **Issue**: The 2026-07-31 fix changed the hook's path arithmetic from one `..` to two (`dirname "$0")/../..`), verified against `scripts/install-hooks.sh` copying the file into `.git/hooks/` (one level deeper than its tracked home in `<repo>/hooks/`). `README.md`'s own "Pre-commit hook (auto mode)" section documents a second method as the first, "recommended" option — `git config --global core.hooksPath d:/codes/my_git_manger/hooks`, pointing straight at the tracked `hooks/` directory, never copying anything into `.git/hooks/`. That method invokes the hook one level shallower than the copied one, so the same two-`..` arithmetic overshoots the repo root by one directory.
- **Root Cause**: `$0`'s location depends entirely on which of two documented, equally-official install methods put the hook there, and the 2026-07-31 fix picked a single hardcoded depth tuned to whichever one the fixing session happened to test against (the one `scripts/sync-main.sh` actually uses in this environment) without checking it against the README's other method.
- **Solution**: Reproduced live: real git repo, `core.hooksPath` set to the tracked `hooks/` dir (no `.git/hooks/` copy), invoked the hook exactly as git would (cwd = repo root, `$0` = the hooksPath-relative absolute path). The two-`..` `SCRIPT` path resolved to one directory above the actual project root; `git_commit.py` wasn't there. Re-verified the *other* method (copy into `.git/hooks/`) still needs the two-`..` depth to work, confirming the two documented methods are simply incompatible with any single `dirname "$0")`-based depth. Fixed by dropping `$0`-relative arithmetic entirely: `SCRIPT="$(git rev-parse --show-toplevel)/git_commit.py"`, which finds the repo root directly regardless of where git invoked the hook from. Verified both methods now resolve to the correct path.
- **Prevention**: When a path is computed relative to `$0`, and the same script is documented to be installed two different ways, a fix verified against one installation is only half-tested — check every officially documented install path before calling a `dirname "$0")`-arithmetic fix complete, or better, avoid `$0`-relative arithmetic entirely when a tool (`git rev-parse --show-toplevel`) can answer the actual question directly.

### 2026-07-26 - `hooks/prepare-commit-msg` was never actually installed as a git hook in this environment
- **Issue**: The 2026-07-23 timeout fix to `hooks/prepare-commit-msg` was verified by rereading the fixed code, never by confirming git would actually execute it. `git config --get core.hooksPath` (both local and `--global`) returned empty, and `.git/hooks/` contained only git's stock `prepare-commit-msg.sample` — no real hook installed.

- **Prevention**: A fix inside a repo-tracked hook script isn't verified until you've confirmed the hook is actually reachable from `.git/hooks/`/`core.hooksPath` in the environment under test — rereading the file's logic verifies the wrong layer. ### 2026-07-18 - Detached HEAD recurs on session start/resume (misdiagnosed on 2026-07-15)
- **Issue**: At least 4 separate DEV.to publishing runs (2026-07-15, 2026-07-16, 2026-07-17→18, 2026-07-18 second run) started with `git status` showing `HEAD detached from refs/heads/main`, with the previous run's own commits floating unreachable from any local branch (though already present on `origin/main` — pushes had succeeded).
- **Root Cause**: The 2026-07-15 article ("My Agent's Git Checkout Left Two Commits Floating in Nowhere") diagnosed this as concurrent agents fighting over one shared working tree's HEAD, and prescribed `git worktree` isolation as the fix. That diagnosis doesn't hold up against the recurrence pattern: this is a single session resuming across scheduled firings, not concurrent sessions. The actual mechanism is environment provisioning — the container that runs each firing is checked out to a specific commit SHA (for reproducibility) rather than the `main` ref, so a fresh or resumed session can start in detached HEAD regardless of how the previous session ended. No amount of "remember to switch back to main before ending the session" discipline prevents this, because it isn't caused by session-end behavior at all.
- **Solution**: `git checkout main && git merge --ff-only <detached-sha>` when the detached commit is a descendant of `main` (verified safe every time so far — pure additions to `issues.md`). Automated as `scripts/sync-main.sh`, safe to run unconditionally at the start of any session that will make new commits.
- **Prevention**: Run `scripts/sync-main.sh` before any git-writing work in this repo. Treat "I fixed it once and wrote it up" as a hypothesis, not a close — a fix that keeps recurring after being documented means the write-up targeted the wrong layer.

### 2026-07-01 - pnpm-workspace pre-commit hook broken on Windows (misleading `ENOENT: git`)
- **Issue**: While committing a fix in `vercel/eve` (a pnpm/Turborepo workspace), `git commit` failed every time with `Error: spawnSync git ENOENT`, seemingly unable to find `git` even though it was on PATH (verified from both git-bash and PowerShell).
- **Root Cause**: The repo's `simple-git-hooks` pre-commit script (`scripts/pre-commit-fmt.mjs`) computed its working directory with `resolve(new URL("..", import.meta.url).pathname)`. On Windows, a `file://` URL's `.pathname` keeps a leading `/` before the drive letter (`/D:/codes/eve/`), so `path.resolve()` produces a bogus `D:\D:\codes\eve`. `spawnSync("git", ..., { cwd: <bogus path> })` then fails with `ENOENT`, and Node blames the command name instead of the invalid `cwd`.
- **Solution**: Manually ran `oxfmt`/`oxlint` on the changed files to replicate what the hook would have done, confirmed clean, then committed with the repo's own `SKIP_SIMPLE_GIT_HOOKS=1` env var (its documented escape hatch — not `git commit --no-verify`).
- **Prevention**: When a Node-based git hook throws `ENOENT` for a command that's clearly on PATH, suspect a bad `cwd`/path derived from `import.meta.url` on Windows (should use `fileURLToPath()`, not `.pathname`) before assuming a PATH problem. Applies to any pnpm/Turborepo-style repo with home-rolled Node hook scripts.
